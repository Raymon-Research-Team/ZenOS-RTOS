# مدل اولویت ZenOS

## تصمیم طراحی

ZenOS عمداً از **۳۲ اولویت واقعی برای Taskها** پشتیبانی می‌کند:

- `0` رزرو شده است و طبق سیاست API می‌تواند به `1` نرمال شود.
- اولویت‌های قابل استفاده `1..31` هستند.
- عدد بزرگ‌تر یعنی اولویت زمان‌بندی بالاتر.
- اولویت‌های `32..255` نامعتبر هستند و باید رد شوند؛ نباید بی‌صدا وارد Scheduler شوند.

این انتخاب عمداً برای **کاهش مصرف RAM** انجام شده است. ZenOS برای ۲۵۶ اولویت، Bitmap یا آرایه ۲۵۶تایی ایجاد نمی‌کند.

## ساختار Scheduler

Scheduler همان ساختارهای ثابت و کم‌مصرف را نگه می‌دارد:

```cpp
uint32_t os_ready_bitmap;
TCB* volatile os_pq_head[32];
```

روی MCUهای ۳۲بیتی، این بخش از حافظه برابر است با:

- Bitmap: چهار بایت
- ۳۲ اشاره‌گر صف: ۱۲۸ بایت
- مجموع: **۱۳۲ بایت**

بنابراین Priority `2` و Priority `3` دو سطح کاملاً مستقل هستند و هر کدام بیت و صف مخصوص خود را دارند.

## چرا ۲۵۶ اولویت نه؟

پیاده‌سازی مستقیم ۲۵۶ سطح حداقل نیاز دارد به:

- ۲۵۶ بیت Bitmap = ۳۲ بایت
- ۲۵۶ اشاره‌گر صف = ۱۰۲۴ بایت روی MCU ۳۲بیتی
- مجموع = **۱۰۵۶ بایت**، پیش از هر bookkeeping اضافی

در مقایسه با ۱۳۲ بایت فعلی، این طراحی حدود **۹۲۴ بایت RAM بیشتر** مصرف می‌کند؛ یعنی تقریباً ۸ برابر storage فعلی مربوط به priority.

این افزایش با هدف ZenOS برای footprint پایین سازگار نیست.

## پیچیدگی

انتخاب سطح آماده از Bitmap سی‌ودودویی استفاده می‌کند و بنابراین روی ۳۲ سطح ثابت انجام می‌شود. عملیات داخل صف همچنان از linked list موجود استفاده می‌کند. بنابراین مستندات ZenOS نباید Scheduler را بدون قید و شرط «O(1) نسبت به تعداد Taskها» معرفی کنند.

## Priority Inheritance / Ceiling

منطق Priority Inheritance و Priority Ceiling همچنان با مقدار واقعی priority کار می‌کند. محدوده معتبر priority همان `1..31` است؛ بنابراین priority حاصل از boost نیز باید در همین محدوده باقی بماند.

## اعتبارسنجی API

Task Creation باید قبل از اضافه‌کردن Task به Ready Queue، priority بزرگ‌تر از `31` را رد کند. این کار از گم‌شدن بی‌صدای priority نامعتبر جلوگیری می‌کند.

## نمونه

| Priority | وضعیت |
|---:|---|
| 0 | رزرو / نرمال‌سازی طبق API |
| 1 | معتبر |
| 2 | معتبر و مستقل از 3 |
| 3 | معتبر و مستقل از 2 |
| 30 | معتبر |
| 31 | بالاترین priority معتبر |
| 32 | نامعتبر |
| 255 | نامعتبر |

مدل نهایی عمداً ساده است: **۳۲ اولویت واقعی، یک بیت برای هر اولویت، بدون banding و بدون RAM اضافه برای Scheduler.**
