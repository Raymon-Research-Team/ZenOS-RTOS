# راهنمای کامل پیکربندی ZenOS RTOS

این سند، **مرجع واحد برای تمام گزینه‌های پیکربندی ZenOS** است. همه تنظیمات در
[`ZenOS/ZenOS_Config.hpp`](../ZenOS/ZenOS_Config.hpp) قرار دارند — تنها فایلی که کاربر برای تنظیم رفتار ویرایش می‌کند.
هر گزینه را می‌توانید با پرچم‌های `-D` کامپایلر یا قبل از نگهبان‌های `#ifndef` در سرآغاز بازنویسی کنید.

**قرارداد نام‌گذاری:**
- `OS_KERNEL_*` — زمان‌بندی و حافظه هسته
- `OS_TOOL_*` — اصول اولیه زمان‌بندی و ارتباط بین‌تسکی
- `OS_MONITOR_*` — قابلیت مشاهده در زمان اجرا
- `OS_SAFETY_*` — تشخیص خطا و حفاظت سخت‌افزاری

**راهنمای یادداشت‌های ایمنی:** [MED-A/B/C] = کلاس‌های پزشکی IEC 62304 · [IND-1..4] = سطوح SIL استاندارد IEC 61508.
اجرای زمان‌کامپایل در [بخش ۹](#۹-اجرای-زمان-کامپایل-استانداردهای-ایمنی) پوشش داده شده است.

</div>

## ۱. Kernel — زمان‌بندی و حافظه هسته

### ۱.۱ `OS_KERNEL_TICK_PERIOD_US` — وضوح تیک
| | |
|---|---|
| **پیش‌فرض** | `100` میکروثانیه (تیک ۱۰ کیلوهرتز) |
| **محدوده** | ۱۰۰ تا ۱۰۰۰، باید ۱۰۰۰ را بخش کند (بررسی زمان‌کامپایل) |
| **ایمنی** | [MED-B] [MED-C] [IND-1] [IND-2] |

وضوح تیک به میکروثانیه. برای کلاس B/C پزشکی و SIL ≥ ۱ باید ≤ ۱ میلی‌ثانیه باشد
(IEC 62304 برای کلاس B/C تحلیل زمان‌بندی می‌خواهد؛ IEC 61508 بخش ۳ جدول ۴ می‌خواهد زمان پاسخ نرم‌افزار به‌طور اثبات‌پذیر کمتر از زمان ایمنی فرایند باشد).

هر تیک = `OS_KERNEL_TICK_PERIOD_US` میکروثانیه؛ بنابراین `os_delay_ms(ms)` به `ms * OS_TICKS_PER_MS` تیک تبدیل می‌شود.

### ۱.۲ `OS_KERNEL_STACK_SIZE` — پشته پیش‌فرض تسک
| | |
|---|---|
| **پیش‌فرض** | `512` بایت |
| **محدوده** | ≥ ۶۴ |
| **ایمنی** | [MED-B] [MED-C] [IND-1] [IND-2] [IND-3] |

اندازه پشته پیش‌فرض هر تسک به بایت. مقدار ۵۱۲ (به‌جای ۲۵۶) حاشیه‌ای برای فریم‌های inlined شده HAL/کتابخانه در `-O2` باقی می‌گذارد؛ گزارش اوج مصرف پشته در خلاصه تست مصرف واقعی را نشان می‌دهد — اگر RAM کم است کوچکش کنید. IEC 62304 §5.4.3 تحلیل مصرف منابع و IEC 61508 بخش ۳ §7.4.3 تحلیل عمق پشته برای همه مسیرهای اجرا را الزامی می‌داند. قاعده سرانگشتی: حداقل ۱۳۰٪ اوج اندازه‌گیری‌شده
(`os_get_stack_usage()` و `os_get_stack_report()`).

### ۱.۳ `OS_KERNEL_MAX_PRIORITIES` — خانه‌های اولویت زمان‌بند
| | |
|---|---|
| **پیش‌فرض** | `32` |
| **محدوده** | ۲ تا ۲۵۶ (بررسی زمان‌کامپایل) |
| **ایمنی** | — |

تعداد خانه‌های اولویت زمان‌بند. اولویت ۰ رزرو است (تسک بیکار)؛ اولویت‌های قابل استفاده `1..OS_KERNEL_MAX_PRIORITIES-1` هستند.

**مدل اولویت زمان‌بند:** هر اولویت قابل استفاده یک سطح مجزای زمان‌بند است — هیچ باندبندی اولویت و هیچ نگاشت `priority >> 3` وجود ندارد.

| خانه‌ها | اولویت‌های قابل استفاده | سر صف‌ها | بیت‌مپ | حافظه پایه اولویت |
|---:|---:|---:|---:|---:|
| ۳۲ | ۱..۳۱ | ۱۲۸ بایت | ۴ بایت | ۱۳۲ بایت |
| ۶۴ | ۱..۶۳ | ۲۵۶ بایت | ۸ بایت | ۲۶۴ بایت |
| ۱۲۸ | ۱..۱۲۷ | ۵۱۲ بایت | ۱۶ بایت | ۵۲۸ بایت |
| ۲۵۶ | ۱..۲۵۵ | ۱۰۲۴ بایت | ۳۲ بایت | ۱۰۵۶ بایت |

بیلد پیش‌فرض ۳۲ اولویتی همان بیت‌مپ اسکالر و ۳۲ سرصف اصلی را نگه می‌دارد، پس پشتیبانی از اولویت پیکربندی‌پذیر به‌صورت پیش‌فرض RAM اضافه نمی‌برد. اولویت‌های بالای ۳۲ از حافظه الحاقی که با ماکروهای مشتق‌شده `OS_PRIORITY_BITMAP_WORDS`، `OS_PRIORITY_EXTRA_COUNT` و `OS_PRIORITY_EXTRA_WORDS` اندازه‌گذاری می‌شود استفاده می‌کنند (اعلام در `ZenOS.hpp` — مقادیر محاسبه‌شده‌اند، تنظیم کاربر نیستند) و فقط وقتی `OS_KERNEL_MAX_PRIORITIES > 32` کامپایل می‌شوند. کنترل round-robin زمان‌بند هم همین قانون را دارد.

**اعتبارسنجی:** ایجاد تسک، اولویت غیرصفر خارج از محدوده پیکربندی‌شده را قبل از درج در صف اولویت رد می‌کند؛ اولویت `0` همان‌طور که قبل بود به `1` نرمال‌سازی می‌شود.

## ۳. Monitor — قابلیت مشاهده در زمان اجرا

### ۳.۱ `OS_MONITOR_DEADLINE` — پایش ددلاین
| | |
|---|---|
| **پیش‌فرض کد** | `0` |
| **محدوده** | 0/1 |
| **ایمنی** | [MED-B] [MED-C] [IND-2] [IND-3] |

تأخیر ددلاین تسک‌ها را تشخیص می‌دهد و واکنش نشان می‌دهد. برای IEC 62304 کلاس B/C (§5.4.3) و IEC 61508 SIL 2+ (بخش ۳ جدول ۵ — پوشش تشخیصی زمان اجرا) الزامی است. تأخیر ددلاین نشان‌دهنده خرابی بالقوه تابع ایمنی است. با فعال شدن، فیلدهای `deadline_ticks` و `deadline_miss_count` به `TCB` اضافه می‌شود؛ ددلاین را با `os_task_set_deadline()` تنظیم و تأخیرها را با `os_get_deadline_miss_count()` بخوانید.

> **توجه:** جدول‌های تاریخی SAFETY_MANUAL پیش‌فرض این گزینه را ۱ گزارش می‌کردند؛ پیش‌فرض کد ۰ است.
> هر وقت تسک‌ها ددلاین دارند آن را فعال کنید (`-DOS_MONITOR_DEADLINE=1`). هنگام هدف‌گذاری کلاس پزشکی B/C یا SIL صنعتی 2+ به‌صورت خودکار اجباری (`#error`) می‌شود.

### ۳.۲ `OS_MONITOR_TCB_INTEGRITY` — بررسی عدد جادوی TCB
| | |
|---|---|
| **پیش‌فرض کد** | `0` |
| **محدوده** | 0/1 |
| **ایمنی** | [MED-C] [IND-3] |

بررسی عدد جادو برای تشخیص خرابی حافظه (IEC 62304 §5.4.4؛ IEC 61508 بخش ۲ جدول ۳ — معیارهای خرابی سخت‌افزاری تصادفی برای داده‌های کنترلی). فیلدهای `magic`/`overflow_count` را به `TCB` اضافه می‌کند. پیش‌فرض کد ۰ است؛ برای کلاس پزشکی C و SIL 3+ الزامی (اجرا‌شده) است.

## ۴. Safety — تشخیص خطا و حفاظت سخت‌افزاری

### ۴.۱ `OS_SAFETY_RAM_TEST` — آزمون پس‌زمینه RAM با March C-
| | |
|---|---|
| **پیش‌فرض کد** | `0` |
| **محدوده** | 0/1 |
| **ایمنی** | [MED-C] [IND-3] [IND-4] |

الگوریتم March C- پس‌زمینه برای یکپارچگی SRAM (IEC 62304 §5.4.4؛ IEC 61508 بخش ۲ جدول ۲ — پوشش تشخیصی خرابی سخت‌افزاری تصادفی RAM). غیرمخرب است اما در حین انتقال‌های فعال DMA ممکن است مثبت کاذب بدهد — `os_ram_test_step()` را فقط از تسک بیکار صدا بزنید. پیش‌فرض کد ۰ است؛ برای کلاس پزشکی C و SIL 3+ الزامی (اجرا‌شده) است.

### ۴.۲ `OS_SAFETY_MPU` — حفاظت سخت‌افزاری حافظه
| | |
|---|---|
| **پیش‌فرض کد** | `0` |
| **محدوده** | 0/1 |
| **ایمنی** | [MED-C] [IND-3] |

حفاظت MPU هر تسک (Cortex-M3/M4/M7). جداسازی مکانی بین نرم‌افزار ایمنی‌مرتبط و غیرایمنی (IEC 62304 §5.4.4؛ IEC 61508 بخش ۲ جدول ۲ — پارتیشن‌بندی مکانی برای SIL 3). نیازمند Cortex-M3 به بالا (Cortex-M0/L0 فاقد MPU هستند — آنجا ۰ بگذارید). پیش‌فرض کد ۰ است؛ برای کلاس پزشکی C و SIL 3+ الزامی است.

### ۴.۳ `OS_SAFETY_HW_WATCHDOG` — تایمر نگهبان سخت‌افزاری (IWDG)
| | |
|---|---|
| **پیش‌فرض کد** | `0` |
| **محدوده** | 0/1 |
| **ایمنی** | [MED-C] [IND-2] [IND-3] |

یکپارچه‌سازی تغذیه/بررسی در سطح سیستم‌عامل؛ خود پریفریال IWDG را CubeMX پیکربندی می‌کند. مکانیسم تحمل خطا (IEC 62304 §5.4.7؛ IEC 61508 بخش ۲ جدول ۲ — پایش خارجی). تسک تغذیه‌کننده باید با دوره ≤ ۵۰٪ تایم‌اوت IWDG اجرا شود. پیش‌فرض کد ۰ است؛ برای کلاس پزشکی C و SIL 2+ الزامی است.

### ۴.۴ `OS_SAFETY_CRC_CHECK` — یکپارچگی ROM با پریفریال CRC
| | |
|---|---|
| **پیش‌فرض کد** | `0` |
| **محدوده** | 0/1 |
| **ایمنی** | [MED-C] [IND-3] [IND-4] |

یکپارچگی فلش را با CRC روی حافظه برنامه بررسی و بیت‌قلب‌های ناشی از تشعشع یا تنش الکتریکی را تشخیص می‌دهد (IEC 62304 §5.4.4؛ IEC 61508 بخش ۲ جدول ۲). حین انجام بررسی روی فلش ننویسید — مثبت کاذب می‌دهد. پیش‌فرض کد ۰ است؛ برای کلاس پزشکی C و SIL 3+ الزامی است.

### ۴.۵ `OS_SAFETY_SOFT_WATCHDOG` — تایمر نرم‌افزاری تسک گیرکرده
| | |
|---|---|
| **پیش‌فرض کد** | `0` |
| **محدوده** | 0/1 |
| **ایمنی** | [MED-B] [MED-C] [IND-1] [IND-2] |

تسک‌های گیرکرده (عدم واگذاری در مهلت `OS_SAFETY_SOFT_WDG_TIMEOUT_MS`) را تشخیص و بازیابی/ریست می‌کند (IEC 62304 §5.4.6؛ IEC 61508 بخش ۳ جدول ۵ — تشخیص خطای نرم‌افزار). تایم‌اوت باید ≤ زمان ایمنی فرایند باشد؛ تسک‌هایی که مشروعاً طولانی اجرا می‌شوند باید دوره‌ای واگذاری کنند. پیش‌فرض کد ۰ است؛ برای کلاس پزشکی B/C و SIL 1+ الزامی است.

### ۴.۶ `OS_SAFETY_DEADLINE_ACTION` — واکنش به تأخیر ددلاین
| | |
|---|---|
| **پیش‌فرض** | `1` |
| **محدوده** | 0 / 1 / 2 (بررسی زمان‌کامپایل) |
| **ایمنی** | [MED-B] [MED-C] [IND-2] [IND-3] |

### ۴.۷ `OS_SAFETY_TASK_MAX_RECOVERY` — حداکثر تلاش بازیابی
| | |
|---|---|
| **پیش‌فرض** | `3` |
| **محدوده** | ≥ ۰ |
| **ایمنی** | [MED-C] [IND-3] |

حداکثر تلاش بازیابی تسک قبل از غیرفعال‌سازی دائمی. پس از تکرار خرابی‌ها سیستم باید به حالت ایمن برود نه اینکه بی‌پایان بازیابی کند. `0` بازیابی را غیرفعال می‌کند (فوراً حالت ایمن).

### ۴.۸ `OS_SAFETY_SOFT_WDG_TIMEOUT_MS` — تایم‌اوت تایمر نرم‌افزاری
| | |
|---|---|

| **ایمنی** | [MED-B] [MED-C] [IND-1] [IND-2] |

باید ≤ زمان ایمنی برنامه / زمان ایمنی فرایند باشد (IEC 62304 §5.4.6؛ IEC 61508 بخش ۱ §7.4.4 — فاصله تست تشخیصی). مقادیر رایج: ۵۰۰ میلی‌ثانیه (کنترل موتور)، ۳۰۰۰ میلی‌ثانیه (فرایند کند).

| | |
|---|---|

| **ایمنی** | [MED-C] [IND-3] |

## ۶. پروفایل‌های آماده پیکربندی

### ۶.۱ حداقلی (دستگاه‌های محدود، زیر ۲۰ کیلوبایت RAM)
```cpp
// ZenOS_Config.hpp — پیکربندی حداقلی
#define OS_KERNEL_TICK_PERIOD_US    1000UL  // تیک ۱ms (سربار کمتر)
#define OS_KERNEL_STACK_SIZE        256     // پشته پیش‌فرض کوچک‌تر

#define OS_TOOL_QUEUE               0
#define OS_TOOL_SEMAPHORE           0
#define OS_TOOL_TICKLESS_IDLE       0

#define OS_MONITOR_DEADLINE         0
#define OS_MONITOR_TCB_INTEGRITY    0
#define OS_MONITOR_ERROR_LOG        0

#define OS_SAFETY_RAM_TEST          0
#define OS_SAFETY_MPU               0
#define OS_SAFETY_HW_WATCHDOG       0
#define OS_SAFETY_CRC_CHECK         0
#define OS_SAFETY_SOFT_WATCHDOG     1       // نگه دارید — تسک گیرکرده را می‌یابد
```

### ۶.۲ استاندارد (پیشنهادی)
```cpp
// ZenOS_Config.hpp — پیکربندی استاندارد: فایل را همان‌طور که هست استفاده کنید؛
// همه موارد منطقی به‌صورت پیش‌فرض فعال‌اند (بخش ۵ را ببینید).
```

### ۶.۳ پروفایل‌های هدف ایمنی
پروفایل‌های هدف ایمنی در سرآغاز پیکربندی ویرایش **نمی‌شوند** — پرچم‌های کامپایلری هستند که گزینه‌های اجباری را در زمان کامپایل اجرا می‌کنند:

```bash
# دستگاه پزشکی — IEC 62304 کلاس B / C
-DOS_TARGET_MEDICAL=2     # کلاس B
-DOS_TARGET_MEDICAL=3     # کلاس C (همه امکانات ایمنی اجباری می‌شوند)

# صنعتی — IEC 61508 SIL 2 / SIL 3
-DOS_TARGET_INDUSTRIAL=2
-DOS_TARGET_INDUSTRIAL=3

# ترکیبی — الزام سخت‌تر اعمال می‌شود
-DOS_TARGET_MEDICAL=3 -DOS_TARGET_INDUSTRIAL=3
```

همه پیش‌فرض‌های کد را فعال نگه دارید و پرچم را اضافه کنید؛ اگر هر ویژگی اجباری غیرفعال باشد، بیلد با `#error` شکست می‌خورد. الزامات دقیق هر سطح را در [بخش ۹](#۹-اجرای-زمان-کامپایل-استانداردهای-ایمنی) ببینید. کلاس پزشکی C و SIL 3 علاوه بر آن، نیاز دارند `OS_MONITOR_DEADLINE`، `OS_MONITOR_TCB_INTEGRITY`، `OS_SAFETY_RAM_TEST`، `OS_SAFETY_MPU`، `OS_SAFETY_HW_WATCHDOG` و `OS_SAFETY_CRC_CHECK` **صریحاً فعال** شوند (به یادداشت‌های بخش‌های ۳ و ۴ مراجعه کنید).

## ۷. نحوه بازنویسی گزینه‌ها

سه روش معادل، به ترتیب اولویت:

۱. **پرچم‌های کامپایلر (سیستم بیلد):**
   ```bash
   CFLAGS += -DOS_KERNEL_TICK_PERIOD_US=1000UL -DOS_SAFETY_MPU=1
   ```
   این روش با به‌روزرسانی کتابخانه بدون دست‌کاری سرآیند منتشرشده باقی می‌ماند.

۲. **ویرایش سرآغاز:** خط `#define` را قبل از نگهبان `#ifndef` گزینه در `ZenOS_Config.hpp` فعال/درج کنید. تا حد ممکن بازنویسی‌های مخصوص پروژه را از فایل توزیع‌شده دور نگه دارید.

۳. **تعریف قبل از include:** گزینه را قبل از include هر سرآغاز ZenOS تعریف کنید؛ نگهبان‌های `#ifndef` به تعریف موجود احترام می‌گذارند.

اعتبارسنجی زمان‌کامپایل مستقل از روش بازنویسی اجرا می‌شود: دوره تیک باید ۱۰۰۰ را بخش کند، `OS_KERNEL_MAX_PRIORITIES` باید ۲ تا ۲۵۶ باشد، `OS_SAFETY_DEADLINE_ACTION` باید 0/1/2 باشد و مقادیر `OS_TARGET_*` باید در محدوده باشند — وگرنه بیلد با `#error` متوقف می‌شود.

## ۸. ثابت‌های مشتق‌شده (تنظیم کاربر نیستند)

این‌ها در `ZenOS.hpp` محاسبه می‌شوند — ویرایش‌شان نکنید:

| ماکرو | تعریف | کاربرد |
|---|---|---|
| `OS_MONITOR_ENABLED` | `1` اگر هرکدام از DEADLINE / TCB_INTEGRITY / ERROR_LOG | گیت API پایش |
| `OS_TICKS_PER_MS` | `1000 / OS_KERNEL_TICK_PERIOD_US` | تبدیل تیک↔میلی‌ثانیه |
| `OS_PRIORITY_BITMAP_WORDS` | `ceil(OS_KERNEL_MAX_PRIORITIES / 32)` | تعداد کلمه‌های بیت‌مپ آماده‌به‌کار |
| `OS_PRIORITY_EXTRA_COUNT` | `MAX_PRIORITIES − 32` (اگر > 32) | خانه‌های سرصف الحاقی |
| `OS_PRIORITY_EXTRA_WORDS` | `ceil(OS_PRIORITY_EXTRA_COUNT / 32)` | کلمه‌های بیت‌مپ الحاقی |
| `OS_IDLE_STACK_WORDS` / `OS_FAULT_STACK_WORDS` | 64 / 48 | اندازه پشته بیکار و خطا |
| `OS_WAIT_FOREVER` | `0xFFFFFFFF` | نشانگر تایم‌اوت بی‌نهایت |
| `OS_VERSION_*` | 1.0.1 | اطلاعات نسخه گزارش‌شده توسط `os_get_version()` |

## ۹. اجرای زمان‌کامپایل استانداردهای ایمنی
