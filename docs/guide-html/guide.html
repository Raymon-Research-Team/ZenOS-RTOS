3.1 Complete main.cppفایل کامل main.cpp

#include "ZenOS.hpp"

/* ─── Task: Blink LED ─── */
void task_blink(void) {
    while (1) {
        HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);  // Toggle LED
        os_delay_ms(500);                          // Wait 500ms
    }
}

/* ─── Main ─── */
int main(void) {
    HAL_Init();
    SystemClock_Config();  // Generated by CubeMX
    MX_GPIO_Init();        // Generated by CubeMX
    MX_TIM1_Init();        // Generated by CubeMX

    os_init();                          // Initialize ZenOS kernel
    os_task_create(task_blink, 5);      // Create task with priority 5
    os_start();                         // Start scheduler (never returns!)

    while (1) {}  // Never reached
}
That's it! The kernel takes over from os_start() and never returns. The task blocks for 500ms between LED toggles, and you don't write scheduling code. همین! هسته سیستم‌عامل از os_start() کنترل را به دست می‌گیرد و هرگز برنمی‌گردد. تسک شما هر ۵۰۰ میلی‌ثانیه اجرا می‌شود، LED چشمک می‌زند، و شما حتی یک خط کد زمان‌بندی هم ننوشتید.

1. Task Managementمدیریت تسک‌ها

What is a Task? A task is an independent function that runs forever in its own context. Think of it as a separate program that runs simultaneously with other tasks. Each task has its own stack (memory for local variables), its own priority (determines execution order), and can be periodic (runs at fixed intervals) or aperiodic (runs whenever scheduled).تسک چیست؟ تسک یک تابع مستقل است که برای همیشه در بافت خودش اجرا می‌شود. آن را به عنوان یک برنامه مستقل در نظر بگیرید که همزمان با تسک‌های دیگر اجرا می‌شود. هر تسک پشته خودش (حافظه برای متغیرهای محلی)، اولویت خودش (ترتیب اجرا) را دارد و می‌تواند دوره‌ای (در فواصل ثابت اجرا می‌شود) یا غیردوره‌ای (هر وقت زمان‌بندی شود اجرا می‌شود) باشد.

How it works: When you call os_task_create(), ZenOS allocates a Task Control Block (TCB) and a stack for the task. The TCB stores the task's state, priority, and context. When os_start() is called, the scheduler begins running the highest-priority ready task. Tasks can block (sleep) using delays or IPC, allowing lower-priority tasks to run.نحوه کار: وقتی os_task_create() را فراخوانی می‌کنید، ZenOS یک بلوک کنترل تسک (TCB) و یک پشته برای تسک تخصیص می‌دهد. TCB وضعیت تسک، اولویت و زمینه را ذخیره می‌کند. وقتی os_start() فراخوانی می‌شود، زمان‌بند شروع به اجرای تسک آماده با بالاترین اولویت می‌کند. تسک‌ها می‌توانند با استفاده از تاخیرها یا IPC بلاک (بخوابند) که به تسک‌های با اولویت پایین‌تر اجازه اجرا می‌دهد.

// Create tasks (call BEFORE os_start())
os_task_create(task_function, priority);              // Default stack (512 bytes)
os_task_create(task_function, priority, period_ms);   // + Periodic
os_task_create_st(task_function, priority, period_ms, stack_bytes); // Custom stack

// Control tasks (call AFTER os_start())
os_task_start(task_function);    // Activate a stopped task
os_task_stop(task_function);     // Deactivate a task
bool running = os_task_isActive(task_function);       // Check state

What happens: os_task_create(task_blink, 5) creates a task named "task_blink" with priority 5. The task will be scheduled to run when os_start() is called. os_task_create(task_sensor, 3, 100) creates a periodic task with a 100ms release interval. os_task_create_st(task_ui, 8, 0, 1024) creates a task with a custom 1KB stack (useful for tasks that use printf or deep function calls).چه اتفاقی می‌افتد: os_task_create(task_blink, 5) یک تسک به نام "task_blink" با اولویت ۵ ایجاد می‌کند. این تسک وقتی os_start() فراخوانی شود زمان‌بندی می‌شود. os_task_create(task_sensor, 3, 100) یک تسک دوره‌ای ایجاد می‌کند که هر ۱۰۰ میلی‌ثانیه اجرا می‌شود. os_task_create_st(task_ui, 8, 0, 1024) یک تسک با پشته سفارشی ۱ کیلوبایت ایجاد می‌کند (برای تسک‌هایی که از printf یا فراخوانی‌های عمیق تابع استفاده می‌کنند مفید است).

2. Timing & Delaysزمان‌بندی و تاخیرها

What is Timing? Timing is how ZenOS keeps track of time and manages task execution intervals. The kernel tick (default 100μs) is the heartbeat of the system — every tick, the scheduler checks which tasks should run. Delays allow tasks to sleep for a specified time, giving other tasks a chance to execute.زمان‌بندی چیست؟ زمان‌بندی نحوه ردیابی زمان و مدیریت فواصل اجرای تسک توسط ZenOS است. تیک هسته (پیش‌فرض ۱۰۰ میکروثانیه) ضربان قلب سیستم است — در هر تیک، زمان‌بند بررسی می‌کند کدام تسک‌ها باید اجرا شوند. تاخیرها به تسک‌ها اجازه می‌دهند برای مدت زمان مشخصی بخوابند و به تسک‌های دیگر فرصت اجرا بدهند.

os_delay_ms(100);  // Sleep ~100ms, yield CPU to other tasks
os_delay_ms(0);    // Immediate yield (gives other tasks a chance)

os_delay_us(10);   // Busy-wait ~10µs (blocks CPU — no other task runs!)

uint32_t ms = os_get_ms();    // Milliseconds since boot
uint32_t us = os_get_us();    // Microseconds since boot (DWT counter)
uint32_t tick = os_get_tick(); // Raw tick count

What happens: os_delay_ms(100) puts the current task to sleep for 100ms. During this time, the scheduler runs other ready tasks. When 100ms passes, the task wakes up and continues. os_delay_ms(0) immediately yields — useful when you want to give other tasks a chance to run without actually sleeping. os_delay_us(10) busy-waits for 10μs — the CPU does nothing else during this time (use only for sub-millisecond delays).چه اتفاقی می‌افتد: os_delay_ms(100) تسک فعلی را به مدت ۱۰۰ میلی‌ثانیه می‌خواباند. در این مدت، زمان‌بند تسک‌های آماده دیگر را اجرا می‌کند. وقتی ۱۰۰ میلی‌ثانیه بگذرد، تسک بیدار شده و ادامه می‌دهد. os_delay_ms(0) فوراً واگذاری می‌کند — مفید وقتی می‌خواهید به تسک‌های دیگر فرصت اجرا بدهید بدون اینکه واقعاً بخوابید. os_delay_us(10) به مدت ۱۰ میکروثانیه انتظار مشغول می‌کشد — CPU در این مدت کار دیگری انجام نمی‌دهد (فقط برای تاخیرهای زیر میلی‌ثانیه استفاده کنید).

os_delay_us() uses DWT cycle counter for busy-waiting. It does NOT yield the CPU. Use only for very short delays (<1ms).os_delay_us() از شمارنده DWT برای انتظار مشغول استفاده می‌کند و CPU را واگذار نمی‌کند. فقط برای تاخیرهای بسیار کوتاه استفاده کنید.

3. Critical Sections (OS_SAFE)بخش‌های بحرانی (OS_SAFE)

What is a Critical Section? A critical section is a piece of code that accesses shared data that might also be accessed by an interrupt service routine (ISR). Without protection, an interrupt could happen in the middle of updating a variable, leaving it in an inconsistent state. OS_SAFE disables all interrupts for the duration of the block, ensuring atomic access to shared data.بخش بحرانی چیست؟ بخش بحرانی قطعه‌ای از کد است که به داده مشترکی دسترسی دارد که ممکن است توسط یک روتین سرویس وقفه (ISR) نیز دسترسی داشته باشد. بدون محافظت، یک وقفه می‌تواند در وسط به‌روزرسانی یک متغیر رخ دهد و آن را در وضعیت ناسازگار باقی بگذارد. OS_SAFE تمام وقفه‌ها را برای مدت بلوک غیرفعال می‌کند و دسترسی اتمی به داده مشترک را تضمین می‌کند.

volatile uint32_t shared_counter = 0;

OS_SAFE {
    shared_counter++;  // Interrupts disabled here
}
// Interrupts re-enabled here

What happens: When the task enters OS_SAFE { ... }, all interrupts are immediately disabled (CPSID I instruction). The code inside the block executes without any interrupt interference. When the block ends, interrupts are re-enabled (CPSIE I). This is implemented using C++ RAII — even if an exception occurs, interrupts are always re-enabled. Keep critical sections short! Long critical sections increase interrupt latency.چه اتفاقی می‌افتد: وقتی تسک وارد OS_SAFE { ... } می‌شود، تمام وقفه‌ها فوراً غیرفعال می‌شوند (دستورالعمل CPSID I). کد داخل بلوک بدون هیچ تداخل وقفه‌ای اجرا می‌شود. وقتی بلوک تمام می‌شود، وقفه‌ها دوباره فعال می‌شوند (دستورالعمل CPSIE I). این با استفاده از RAII C++ پیاده‌سازی می‌شود — حتی اگر خطایی رخ دهد، وقفه‌ها همیشه دوباره فعال می‌شوند. بخش‌های بحرانی را کوتاه نگه دارید! بخش‌های بحرانی طولانی تاخیر وقفه را افزایش می‌دهند.

4. Events (OS_EVENT)رویدادها (OS_EVENT)

What is an Event? An event is a synchronization primitive used for inter-task signaling. Think of it as a "flag" that one task can raise (signal) and another task can wait for. Events use an internal counter — each signal() increments the counter, and each wait() decrements it (if > 0) or blocks until signaled or timeout. This makes events perfect for ISR-to-task communication and simple synchronization.رویداد چیست؟ رویداد یک اولیه همگام‌سازی برای سیگنال‌دهی بین تسک‌ها است. آن را به عنوان یک "پرچم" در نظر بگیرید که یک تسک می‌تواند آن را بالا ببرد (سیگنال) و تسک دیگری منتظر آن باشد. رویدادها از یک شمارنده داخلی استفاده می‌کنند — هر signal() شمارنده را افزایش می‌دهد و هر wait() آن را کاهش می‌دهد (اگر > ۰ باشد) یا تا سیگنال یا تایم‌اوت بلاک می‌شود. این رویدادها را برای ارتباط ISR-to-task و همگام‌سازی ساده عالی می‌کند.

OS_EVENT sensor_ready;  // Create an event

// Waiter task (waits for the event):
if (sensor_ready.wait(1000)) {  // Wait up to 1000ms
    process_sensor_data();      // Event was signaled!
} else {
    handle_timeout();           // Timeout — no signal received
}

// Signaler task (signals the event):
read_sensor();
sensor_ready.signal();  // Wake up the waiter

// ISR-safe signaling (use in interrupt handlers):
sensor_ready.signal_from_isr();

What happens: Task A calls sensor_ready.wait(1000) and blocks (sleeps). Task B reads a sensor, then calls sensor_ready.signal(). This wakes up Task A, which then processes the data. If Task B doesn't signal within 1000ms, Task A wakes up with false (timeout). Important: Always use signal_from_isr() in interrupt handlers — calling signal() from an ISR is undefined behavior.چه اتفاقی می‌افتد: تسک A فراخوانی sensor_ready.wait(1000) می‌کند و بلاک (می‌خوابد). تسک B یک حسگر می‌خواند، سپس sensor_ready.signal() را فراخوانی می‌کند. این تسک A را بیدار می‌کند که سپس داده را پردازش می‌کند. اگر تسک B ظرف ۱۰۰۰ میلی‌ثانیه سیگنال ندهد، تسک A با false (تایم‌اوت) بیدار می‌شود. مهم: همیشه از signal_from_isr() در روتین‌های وقفه استفاده کنید — فراخوانی signal() از ISR رفتار تعریف نشده است.

Signal Accumulationتجمع سیگنال

OS_EVENT evt;

evt.signal();  // count = 1
evt.signal();  // count = 2
evt.signal();  // count = 3

evt.wait();    // count = 2 (returns 1)
evt.wait();    // count = 1 (returns 1)
evt.wait();    // count = 0 (returns 1)
evt.wait();    // returns 0 (timeout — count was already 0)

What happens: Multiple signals accumulate in the counter. Each wait() consumes one signal. If 3 signals are sent before any wait, the first 3 waits return immediately (count > 0). The 4th wait blocks until a new signal arrives or timeout. Use case: Multiple ISRs can signal the same event, and the task processes all pending signals one by one.چه اتفاقی می‌افتد: سیگنال‌های متعدد در شمارنده تجمع می‌یابند. هر wait() یک سیگنال مصرف می‌کند. اگر ۳ سیگنال قبل از هر wait ارسال شود، ۳ wait اول فوراً برمی‌گردند (count > ۰). wait چهارم تا رسیدن سیگنال جدید یا تایم‌اوت بلاک می‌شود. مورد استفاده: ISR‌های متعدد می‌توانند به یک رویداد سیگنال بدهند و تسک تمام سیگنال‌های معلق را یکی یکی پردازش می‌کند.

5. Mutexes (OS_MUTEX)قفل‌ها (OS_MUTEX)

What is a Mutex? A mutex (mutual exclusion) is a lock that ensures only one task can access a shared resource at a time. Think of it as a key to a room — only the task holding the key (locked mutex) can enter the room (use the resource). When the task leaves, it returns the key (unlocks), allowing another task to enter. ZenOS mutexes support recursive locking (same task can lock multiple times) and IPC ceiling (prevents priority inversion).Mutex چیست؟ mutex (حذف متقابل) یک قفل است که تضمین می‌کند فقط یک تسک در هر زمان بتواند به یک منبع مشترک دسترسی داشته باشد. آن را به عنوان کلید یک اتاق در نظر بگیرید — فقط تسکی که کلید (قفل mutex) را در اختیار دارد می‌تواند وارد اتاق (منبع را استفاده کند) شود. وقتی تسک خارج می‌شود، کلید را برمی‌گرداند (قفل را باز می‌کند) و به تسک دیگری اجازه ورود می‌دهد. mutex‌های ZenOS از قفل بازگشتی (همین تسک می‌تواند چندین بار قفل کند) و سقف IPC (جلوگیری از وارونگی اولویت) پشتیبانی می‌کنند.

OS_MUTEX uart_mtx;  // Create a mutex for UART

// RAII lock guard (auto-unlocked when block ends)
OS_LOCK(uart_mtx) {  // Acquire mutex
    HAL_UART_Transmit(&huart1, data, len, 100);  // Use resource
}  // Auto-released when block ends

// Manual lock/unlock
if (mtx.lock(1000)) {  // Wait up to 1000ms
    do_work();
    mtx.unlock();
}

// With IPC ceiling (priority inheritance)
OS_MUTEX shared_data_mtx(8);  // Ceiling priority = 8

What happens: When Task A enters OS_LOCK(uart_mtx), it acquires the mutex. If Task B tries to enter while Task A holds it, Task B blocks until Task A exits. OS_LOCK is an RAII guard — it automatically releases the mutex when the block ends. IPC Ceiling: When you pass a ceiling priority (e.g., OS_MUTEX mtx(8)), the task's priority is temporarily boosted to that level while holding the mutex, preventing priority inversion.چه اتفاقی می‌افتد: وقتی تسک A وارد OS_LOCK(uart_mtx) می‌شود، mutex را به دست می‌آورد. اگر تسک B سعی کند وارد شود در حالی که تسک A آن را نگه داشته، تسک B بلاک می‌شود تا تسک A خارج شود. OS_LOCK یک محافظ RAII است — به طور خودکار mutex را آزاد می‌کند. سقف IPC: اولویت تسک به طور موقت به سطح سقف افزایش می‌یابد و از وارونگی اولویت جلوگیری می‌کند.

6. Queues (OS_QUEUE)صفوف (OS_QUEUE)

What is a Queue? A queue is a FIFO (First-In-First-Out) data structure for passing data between tasks or from ISRs to tasks. Think of it as a pipe — one task puts data in one end, and another task takes it out the other end. Queues are type-safe (using C++ templates), thread-safe, and can hold a fixed number of items. If the queue is full, the producer can wait or drop the data. If empty, the consumer can wait or timeout.صف چیست؟ صف یک ساختمان داده FIFO (اول وارد شده، اول خارج شده) برای انتقال داده بین تسک‌ها یا از ISRs به تسک‌هاست. آن را به عنوان یک لوله در نظر بگیرید — یک تسک داده را در یک انتها می‌گذارد و تسک دیگر آن را از انتهای دیگر بیرون می‌آورد. صف‌ها ایمن از نظر نوع (با الگوهای C++), ایمن از نظر رشته‌ای هستند و تعداد ثابتی آیتم نگه می‌دارند. اگر صف پر باشد، تولیدکننده می‌تواند منتظر بماند یا داده را رها کند.

How it works: When you declare OS_QUEUE<int, 8> sensor_queue;, ZenOS reserves space for 8 integers in a circular buffer. put() adds an item to the tail, get() removes from the head. If the queue is full and you call put() with a timeout, the task blocks until space is available. If the queue is empty and you call get(), the task blocks until data arrives.نحوه کار: وقتی OS_QUEUE<int, 8> sensor_queue; را اعلام می‌کنید، ZenOS فضایی برای ۸ عدد در بافر دایره‌ای رزرو می‌کند. put() آیتمی به انتها اضافه می‌کند، get() از سر حذف می‌کند. اگر صف پر باشد و put() را با تایم‌اوت فراخوانی کنید، تسک تا فراهم شدن فضا بلاک می‌شود.

OS_QUEUE<int, 8> sensor_queue;  // Capacity: 8 items of type int

// Producer — puts data into the queue:
sensor_queue.put(42);              // Non-blocking: add 42 to queue
sensor_queue.put(100, 100);        // Blocking: wait up to 100ms if full

// Consumer — gets data from the queue:
int value;
if (sensor_queue.get(value, 1000)) {  // Wait up to 1000ms
    process(value);                    // Got data!
} else {
    handle_timeout();                  // No data within 1000ms
}

// ISR-safe (use in interrupt handlers):
sensor_queue.put_from_isr(val);    // Signal from ISR to task

// Check queue status:
bool empty = sensor_queue.is_empty();
bool full  = sensor_queue.is_full();
uint8_t count = sensor_queue.count();  // Items waiting

Example output: If the sensor task puts values 10, 20, 30 into the queue, and the consumer calls get() three times, it receives 10, then 20, then 30 (FIFO order). If the consumer calls get() when the queue is empty, it blocks until data arrives or timeout.مثال: اگر تسک حسگر مقادیر ۱۰، ۲۰، ۳۰ را در صف بگذارد و مصرف‌کننده سه بار get() فراخوانی کند، به ترتیب ۱۰، سپس ۲۰، سپس ۳۰ دریافت می‌کند (ترتیب FIFO). اگر مصرف‌کننده وقتی صف خالی است get() فراخوانی کند، تا رسیدن داده یا تایم‌اوت بلاک می‌شود.

Queue for Sensor Data Pipelineصف برای خط لوله داده حسگر

struct SensorData {
    uint16_t temperature;
    uint16_t humidity;
    uint32_t timestamp;
};

OS_QUEUE<SensorData, 16> data_queue;  // Queue of 16 SensorData structs

// Task 1: Read sensor every 100ms
void task_reader(void) {
    while (1) {
        SensorData d;
        d.temperature = ADC_ReadTemp();
        d.humidity = ADC_ReadHumidity();
        d.timestamp = os_get_ms();
        data_queue.put(d, 50);  // Wait max 50ms if full
        os_delay_ms(100);
    }
}

// Task 2: Send data to UART
void task_sender(void) {
    while (1) {
        SensorData d;
        if (data_queue.get(d, 1000)) {
            printf("T=%u H=%u\n", d.temperature, d.humidity);
        }
    }
}

What happens: Task 1 reads sensor data every 100ms and puts it into the queue. Task 2 waits for data and sends it over UART. If Task 2 is slower than Task 1, the queue fills up and Task 1 waits. If Task 2 is faster, it waits for new data. The queue acts as a buffer between the two tasks, decoupling their speeds.چه اتفاقی می‌افتد: تسک ۱ هر ۱۰۰ میلی‌ثانیه داده حسگر را می‌خواند و در صف می‌گذارد. تسک ۲ منتظر داده می‌ماند و آن را از UART ارسال می‌کند. اگر تسک ۲ کندتر از تسک ۱ باشد، صف پر شده و تسک ۱ منتظر می‌ماند. صف به عنوان بافر بین دو تسک عمل می‌کند و سرعت آن‌ها را از هم جدا می‌کند.

7. Semaphores (OS_SEMAPHORE)سمافورها (OS_SEMAPHORE)

What is a Semaphore? A semaphore is a counter-based synchronization primitive. Think of it as a pool of resources — the counter represents the number of available resources. wait() decrements the counter (takes a resource), and signal() increments it (returns a resource). If the counter is 0, wait() blocks until someone signals. Semaphores are perfect for limiting concurrent access to a resource pool (e.g., 5 available buffers, 3 UART ports).سمافور چیست؟ سمافور یک اولیه همگام‌سازی مبتنی بر شمارنده است. آن را به عنوان مجموعه‌ای از منابع در نظر بگیرید — شمارنده تعداد منابع موجود را نشان می‌دهد. wait() شمارنده را کاهش می‌دهد (منبعی برمی‌دارد) و signal() آن را افزایش می‌دهد (منبعی برمی‌گرداند). اگر شمارنده ۰ باشد، wait() تا سیگنال کسی بلاک می‌شود. سمافورها برای محدود کردن دسترسی همزمان به مجموعه منابع عالی هستند.

OS_SEMAPHORE(5) resource_sem;  // Max 5 concurrent users

// Task that uses a shared resource:
if (resource_sem.wait(1000)) {  // Wait for available resource
    use_resource();              // Use the resource
    resource_sem.signal();       // Return the resource
}

What happens: Imagine you have 5 buffer slots. Each task calls resource_sem.wait() before using a buffer (counter decrements: 5→4→3→...). When all 5 are in use, the next task blocks. When a task calls resource_sem.signal(), the counter increments and the next waiting task wakes up.چه اتفاقی می‌افتد: فرض کنید ۵ اسلات بافر دارید. هر تسک قبل از استفاده از بافر resource_sem.wait() فراخوانی می‌کند (شمارنده کاهش: ۵→۴→۳→...). وقتی همه ۵ در حال استفاده باشند، تسک بعدی بلاک می‌شود. وقتی تسکی resource_sem.signal() فراخوانی می‌کند، شمارنده افزایش یافته و تسک منتظر بیدار می‌شود.

// Example: Limit UART access to 1 task at a time
OS_SEMAPHORE(1) uart_sem;  // Binary semaphore (max=1)

void task_send(const char* msg) {
    if (uart_sem.wait(500)) {
        HAL_UART_Transmit(&huart1, msg, strlen(msg), 100);
        uart_sem.signal();
    }
}

8. Periodic Tasksتسک‌های دوره‌ای

Periodic task model: ZenOS stores the period supplied as the third argument of os_task_create() in the task control block. In the current kernel, period_ticks and next_run_time are maintained by the PendSV path, but the ready-queue selection does not yet use them as a blocking gate. Therefore, documentation must not claim that period_ms alone currently wakes a task at fixed intervals.مدل تسک دوره‌ای: ZenOS دوره‌ای را که به‌عنوان آرگومان سوم os_task_create() داده می‌شود، در ساختار کنترل تسک نگهداری می‌کند. در هسته فعلی، فیلدهای period_ticks و next_run_time در مسیر PendSV به‌روزرسانی می‌شوند، اما انتخاب تسک آماده هنوز از آن‌ها به‌عنوان شرط توقف استفاده نمی‌کند. بنابراین، مستندات نباید ادعا کنند که period_ms به‌تنهایی در نسخه فعلی، اجرای تسک را در فواصل ثابت بیدار می‌کند.

void task_sensor(void) {
    while (1) {
        uint16_t val = ADC_Read();
        sensor_queue.put(val, 100);

        // Give the scheduler a chance to run another ready task.
        os_yield();
    }
}

// The period is recorded in the TCB.
// Do not describe it as an enforced wake-up interval
// until the scheduler's period gate is enabled.
os_task_create(task_sensor, 3, 100);

Why os_yield() here? A periodic-task example should use os_yield(), not an arbitrary os_delay_ms() value, when the intention is to demonstrate cooperative rescheduling. os_delay_ms() is a real blocking delay and should be documented separately as a sleep primitive.چرا اینجا os_yield()؟ در مثال یک تسک دوره‌ای، وقتی هدف نشان‌دادن واگذاری اجرای CPU است، باید از os_yield() استفاده شود، نه یک مقدار دلخواه برای os_delay_ms(). تابع os_delay_ms() یک تأخیر واقعی و مسدودکننده است و باید جداگانه به‌عنوان primitive خواب‌دادن تسک توضیح داده شود.

Periodic release: The scheduler checks next_run_time before selecting a periodic task. The task should call os_yield() after its work; os_delay_ms() remains a separate blocking sleep primitive.اجرای دوره‌ای: زمان‌بند پیش از انتخاب تسک دوره‌ای، next_run_time را بررسی می‌کند. تسک باید پس از انجام کار از os_yield() استفاده کند؛ os_delay_ms() همچنان یک primitive برای خواب و تأخیر مسدودکننده است.

Periodic vs One-Shot Tasksدوره‌ای در مقابل یکبار اجرا

// Periodic: released every 50ms
os_task_create(task_blink, 5, 50);  // 3rd param = period

// Aperiodic task: period = 0 means no release gate
os_task_create(task_handler, 5, 0);
// Stop/start explicitly when event-driven control is required:
os_task_stop(task_handler);
os_task_start(task_handler);

What happens: A task with period 50 becomes eligible again at each 50ms release boundary after it yields. A period of 0 means the task has no periodic release gate; it remains schedulable until you explicitly stop it.چه اتفاقی می‌افتد: تسک دوره‌ای با دوره ۵۰ هر ۵۰ میلی‌ثانیه توسط زمان‌بند به طور خودکار بیدار می‌شود. تسک یکبار اجرا (دوره=۰) تا فراخوانی os_task_start() غیرفعال می‌ماند — برای تسک‌های رویدادمحور مفید است که فقط وقتی فعال می‌شوند اجرا می‌شوند.

Complete Example: Sensor + LED Systemمثال کامل: سیستم حسگر + LED

OS_QUEUE<uint16_t, 8> temp_queue;
OS_EVENT temp_ready;

// Periodic sensor task (200ms release interval)
void task_sensor(void) {
    while (1) {
        uint16_t temp = read_temperature();
        temp_queue.put(temp, 50);
        temp_ready.signal();           // Notify processing task
        os_yield();                    // Yield to the scheduler
    }
}

// Processing task (waits for sensor data)
void task_process(void) {
    while (1) {
        if (temp_ready.wait(500)) {
            uint16_t temp;
            if (temp_queue.get(temp, 100)) {
                if (temp > 3000) {     // > 30°C
                    HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, 0);  // LED ON
                } else {
                    HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, 1);  // LED OFF
                }
            }
        }
    }
}

int main(void) {
    // ... HAL init ...
    os_init();
    os_task_create(task_sensor, 3, 200);   // 200ms period
    os_task_create(task_process, 5, 0);    // Event-driven
    os_start();
}

What happens: At each 200ms release boundary, task_sensor becomes eligible, reads the temperature and signals task_process. task_process waits for the signal, reads the temperature from the queue, and turns the LED on/off based on the value. This demonstrates periodic tasks, queues, and events working together.چه اتفاقی می‌افتد: هر ۲۰۰ میلی‌ثانیه، task_sensor دما را می‌خواند و task_process را سیگنال می‌دهد. task_process منتظر سیگنال می‌ماند، دما را از صف می‌خواند و LED را بر اساس مقدار روشن/خاموش می‌کند. این نشان می‌دهد تسک‌های دوره‌ای، صف‌ها و رویدادها چگونه با هم کار می‌کنند.

9. Monitoring & Debuggingپایش و دیباگ

Why Monitor? In embedded systems, debugging is hard — you often can't attach a debugger to production devices. ZenOS provides built-in monitoring tools that help you track stack usage, CPU load, deadline compliance, and errors. These tools run in the background with minimal overhead, giving you visibility into your system's health without affecting real-time performance.چرا پایش؟ در سیستم‌های توکار، دیباگ سخت است — اغلب نمی‌توانید به دستگاه‌های تولیدی دیباگر وصل کنید. ZenOS ابزارهای پایش داخلی ارائه می‌دهد که به ردیابی مصرف پشته، بار CPU، رعایت ددلاین و خطاها کمک می‌کنند. این ابزارها در پس‌زمینه با حداقل سربار اجرا می‌شوند.

If a task has a 512-byte stack and uses 480 bytes, you're close to overflow — increase the stack size. os_get_cpu_usage_total() returns total CPU utilization (0-100%). If it's above 80%, your system is overloaded. os_get_task_cpu_usage() shows which task is consuming the most CPU.چه اتفاقی می‌افتد: os_get_stack_usage() تعداد بایت‌های استفاده شده از پشته تسک را برمی‌گرداند. اگر تسکی پشته ۵۱۲ بایتی دارد و ۴۸۰ بایت استفاده کرده، نزدیک به سرریز هستید — پشته را بزرگ‌تر کنید. os_get_cpu_usage_total() کل استفاده CPU را برمی‌گرداند (۰-۱۰۰٪). اگر بالای ۸۰٪ باشد، سیستم بیش از حد بارگذاری شده است.

🔌 Serial Output (printf)خروجی سریال (printf)

Why Serial Output? In embedded development, you can't use a graphical debugger in production. Serial output (via UART) is your window into the system — it lets you print debug messages, sensor values, and system status. ZenOS provides a simple way to redirect printf() to UART so you can see what's happening in real-time.چرا خروجی سریال؟ در توسعه توکار، نمی‌توانید از دیباگر گرافیکی در تولید استفاده کنید. خروجی سریال (از طریق UART) پنجره شما به سیستم است — به شما اجازه می‌دهد پیام‌های دیباگ، مقادیر حسگر و وضعیت سیستم را چاپ کنید.

#include <cstdio>

    os_event_signal(-1);  // Deliberately invalid — expected error

Task Lifecycle Managementمدیریت چرخه حیات تسک

Why Control Task Lifecycle? In many systems, you don't want all tasks running all the time. For example, a heater task should only run when temperature is low. ZenOS lets you start and stop tasks dynamically at runtime, saving CPU and power.چرا کنترل چرخه حیات تسک؟ در بسیاری از سیستم‌ها، نمی‌خواهید تمام تسک‌ها همیشه اجرا شوند. مثلاً تسک هیتر فقط وقتی دما پایین است باید اجرا شود.

// Pre-create all tasks, start/stop as needed
os_task_create(task_heater, 5);
os_task_create(task_cooler, 5);
os_task_stop(task_heater);   // Start inactive
os_task_stop(task_cooler);   // Start inactive

// Runtime control
if (temperature > 70) {
    os_task_start(task_cooler);    // Activate cooler
    os_task_stop(task_heater);     // Deactivate heater
} else if (temperature < 20) {
    os_task_start(task_heater);    // Activate heater
    os_task_stop(task_cooler);     // Deactivate cooler
}

What happens: Tasks are created but immediately stopped (dormant). They don't use CPU until os_task_start() is called. This is more efficient than creating/destroying tasks repeatedly. The task's stack and TCB remain allocated but the scheduler ignores stopped tasks.چه اتفاقی می‌افتد: تسک‌ها ایجاد اما فوراً متوقف می‌شوند (غیرفعال). تا فراخوانی os_task_start() از CPU استفاده نمی‌کنند.

Power Management with Tickless Idleمدیریت مصرف با حالت idle بدون تیک

What is Tickless Idle? In normal mode, the SysTick interrupt fires every 100μs even when nothing is happening — wasting power. Tickless idle disables SysTick during long delays and uses a hardware timer to wake up exactly when the next task is due. This dramatically reduces power consumption in battery-powered devices.idle بدون تیک چیست؟ در حالت عادی، وقفه SysTick هر ۱۰۰ میکروثانیه حتی وقتی هیچ اتفاقی نمی‌افتد فعال می‌شود — مصرف بیهوده انرژی. idle بدون تیک SysTick را در تاخیرهای طولانی غیرفعال کرده و از تایمر سخت‌افزاری برای بیدار کردن دقیقاً وقتی تسک بعدی لازم است استفاده می‌کند.

State Machine in a Taskماشین حالت در یک تسک

enum State { INIT, RUNNING, ERROR, SLEEP };
static State state = INIT;

void task_state_machine(void) {
    while (1) {
        switch (state) {
            case INIT:
                if (hardware_ready()) state = RUNNING;
                break;
            case RUNNING:
                if (error_detected()) state = ERROR;
                else do_work();
                break;
            case ERROR:
                if (error_cleared()) state = RUNNING;
                else enter_safe_state();
                break;
            case SLEEP:
                os_delay_ms(1000);
                break;
        }
        os_yield();        // Always yield
    }
}
